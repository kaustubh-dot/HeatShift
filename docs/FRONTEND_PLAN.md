# HeatShift Frontend Implementation Plan

This is the execution plan for the interface defined in [DESIGN.md](DESIGN.md). It is intentionally narrower than the design system: the goal is to ship one polished, evidence-rich demo before the hackathon deadline, not to build a reusable component library.

## 1. Delivery constraint and success test

The submission deadline is **5 August 2026 at 17:00 EDT** according to the [OrionHackathon Devpost page](https://orionhackathon.devpost.com/). The frontend therefore has a hard implementation budget of roughly **18–22 focused hours after genuine solver fixtures exist**.

The build succeeds when a judge can answer these questions within 30 seconds:

1. What operational problem is HeatShift solving?
2. What changed when the heat policy was enforced?
3. Why was one work order deferred?
4. Which claims were proven by the solver, and which were not?

The interface must reinforce the judging criteria: technical evidence, real-world impact, usability, and a clear demo story. Visual polish is valuable only when it makes those facts easier to see.

## 2. Non-negotiable release slice

### Must ship

- Three click-driven chapters: Tomorrow's Brief, Plan Transformation, and Why / What-if.
- A complete 07:00–17:00 overview with all 40 slots visible at the 1280px presentation viewport.
- Service-first versus policy-constrained metrics and solver-provided plan differences.
- One solver-derived deferred-job diagnosis with proof status and retained commitments.
- The +2°C re-solve with a meaningful result change.
- Honest `OPTIMAL`, `FEASIBLE`, `INFEASIBLE`, `UNKNOWN`, and `MODEL_INVALID` presentation.
- A clearly disclosed saved-results fallback generated by the real solver.
- Keyboard operation, visible focus, readable contrast, and reduced-motion behavior.
- One production command that serves the UI and API from the same origin.

### Polish if the core is stable

- Synchronized selection across timeline, map, and diff list.
- A 1.6-second-or-shorter plan transformation animation with replay.
- Ambient thermal wash and restrained grain.
- Route crossfades and metric count transitions.

### Cut first

- Animated route drawing.
- Per-component bespoke tooltips.
- A full work-order browser on Chapter 1.
- Counter animations and decorative loading effects.
- Any abstraction created for hypothetical future screens.

Do not cut the timeline, solver evidence, diagnosis, heat shock, fallback disclosure, or accessibility.

## 3. Technical stack

Use the smallest stack that preserves the required experience:

| Area | Choice | Reason |
|---|---|---|
| UI | React + TypeScript + Vite | Matches the locked architecture and supports a fast production build |
| State | React `useReducer` + context at the app boundary | The application has one linear three-chapter flow; a state library is not yet justified |
| Styling | Vanilla CSS and custom properties | Direct control over the OKLCH palette, grid, and motion |
| Requests | Native `fetch` + `AbortController` | No client library is needed for three endpoints |
| Icons | `lucide-react` only | Consistent accessible icon geometry without hand-authored SVGs |
| Tests | Vitest + React Testing Library | Focused behavior and accessibility coverage |

Pin exact resolved versions in `package-lock.json`. Do not maintain loose version claims in this document. Do not add Zustand, a router, animation framework, CSS framework, `clsx`, or MSW unless a concrete implementation problem proves the need.

Use CSS transitions or the Web Animations API for the signature transformation. The reduced-motion path must work without a motion package.

### Fonts

Bundle licensed WOFF2 files for Space Grotesk, DM Sans, and JetBrains Mono under `frontend/public/fonts/`. Use `font-display: swap` and the system fallbacks defined in [DESIGN.md](DESIGN.md). The live demo must not depend on Google Fonts or any other CDN.

## 5. Contract boundary

[DATA_AND_API_CONTRACTS.md](DATA_AND_API_CONTRACTS.md) is the source of truth. `types.ts` mirrors it; this plan does not duplicate the full schema because duplicated contracts drift.

The frontend may format and select backend facts. It must not:

- calculate heat-policy compliance;
- recompute metrics or objective deltas;
- infer why a work order moved or was deferred;
- turn `FEASIBLE` into “maximum”; or
- turn `UNKNOWN` into “impossible.”

Before styling a fixture, add a contract test that parses the saved result and checks the fields used by the UI. If the backend schema changes, update the canonical contract first, then the TypeScript types and fixture together.

### Endpoint use

| Endpoint | UI use |
|---|---|
| `GET /api/demo` | Load scenario, policy, and display coordinates |
| `POST /api/solve` | Load service-first and policy-constrained results; send `heat_adjustment_c: 2` for heat shock |
| `POST /api/diagnose` | Load the selected deferred job's forced-inclusion analysis |

Do not assume that optional saved-result **metadata** returned by `GET /api/demo` is a complete `SolveResponse`. The self-contained presentation fallback is loaded from `/fallback/demo.json`.

## 6. Application state

Keep one reducer-owned state object:

```typescript
type ChapterId = 'brief' | 'plan' | 'why';
type DataSource = 'live' | 'saved';

interface AppState {
  chapter: ChapterId;
  scenario: Scenario | null;
  policy: Policy | null;
  solveResult: SolveResponse | null;
  heatShockResult: SolveResponse | null;
  diagnoses: Record<string, DiagnosisResponse>;
  selectedJobId: string | null;
  selectedCrewId: string | null;
  dataSource: DataSource;
  request: {
    demo: RequestState;
    solve: RequestState;
    diagnosis: RequestState;
    heatShock: RequestState;
  };
}
```

Plans, metrics, differences, deferred jobs, and selected details are derived from these canonical responses. Do not also store `serviceFirstPlan`, `policyPlan`, or copied metric values; duplicate state creates stale comparisons.

Keep hover state and animation phase local to the visualization that owns it. Store only cross-view selection globally.

## 7. Loading, failure, and fallback rules

### Request behavior

- Use one 15-second browser request timeout. The backend owns its per-stage solver time limits.
- Preserve the current result while a re-solve is running.
- Disable only the action that initiated the request.
- Announce progress with `role="status"` and `aria-live="polite"`; never trap focus in a loading overlay.
- Render a successful `FEASIBLE` response as a result with “optimality not proven,” not as an error.
- Use the structured API error envelope for invalid input, model errors, and no-result timeouts.

### Fallback activation

Fallback mode may activate when:

1. `?fallback=true` is present;
2. `VITE_FALLBACK_MODE=true`; or
3. the API is unreachable or returns a server failure.

Do not silently fall back for a 4xx validation response or a malformed success payload; those are product defects that must remain visible.

For `solve` and `diagnose`, a saved answer may be substituted only when the complete submitted scenario and policy match the locked fixture structurally, the heat adjustment matches, and the diagnosed job matches a precomputed entry. Otherwise show the failure. Never present a saved answer as if it were computed for arbitrary inputs.

While saved data is active, keep a non-dismissible trust message visible:

> SAVED SOLVER RUN · Live API unavailable · Results generated from the locked demo scenario

Include a generated timestamp or fixture version in the detail view. The banner is evidence of resilience, not something to hide.

## 8. Chapter implementation

### Chapter 1 — Tomorrow's Brief

The first frame should be an editorial brief, not a dashboard inventory.

- Lead with `41°C`, the one-sentence problem, and a single “Generate policy-constrained plan” action.
- Render the supplied heat series as discrete 15-minute bands.
- Show three crews as one compact identity row.
- Spotlight no more than three work orders that matter to the later transformation.
- State “12 work orders” as a summary; put the full list behind a secondary “Inspect scenario” disclosure only if time allows.
- Preload the locked demo automatically. Do not require file upload or configuration before the first meaningful screen.

The chapter exit must lead directly into the service-first plan, then visibly transform it into the policy-constrained plan.

### Chapter 2 — Plan Transformation

This is the signature screen and receives most of the frontend budget.

At 1280px:

- Keep the metrics strip across the top.
- Use a compact schematic map beside the timeline.
- Keep the complete 10-hour timeline visible without horizontal scrolling in overview mode.
- Place the short plan-diff list below or beside the timeline without hiding the primary evidence.
- Always show the policy-constrained plan after the transition; offer “Replay change” instead of leaving the interface in an ambiguous midway state.

The visual order is:

1. service-first plan appears;
2. changed segments highlight;
3. moved/deferred/recovery segments transition together;
4. policy-constrained metrics and proof status settle;
5. the result remains static and inspectable.

Total animation must be at most 1.6 seconds. Do not wait for animation before making the final facts available to assistive technology.

### Chapter 3 — Why / What-if

- Default to the strongest solver-derived deferred-job example from the genuine fixture.
- Lead with the classification and plain-language consequence.
- Show retained commitments, displaced jobs, objective delta, binding rule IDs, and tested interventions.
- Keep proof status adjacent to the classification.
- Make “Apply +2°C Heat Shock” the only primary action.
- After the shock, state the decision change before showing supporting details.

If no deferred job exists, the scenario has failed a release gate; do not invent a diagnosis to rescue the UI.

## 9. Timeline implementation

Use slot indices as layout coordinates, not fixed pixel arithmetic.

```css
.timeline-track {
  display: grid;
  grid-template-columns: repeat(var(--slot-count), minmax(0, 1fr));
}
```

```tsx
<button
  className="timeline-segment"
  style={{ gridColumn: `${segment.start_slot + 1} / ${segment.end_slot + 1}` }}
/>
```

Keep crew labels in a separate fixed column. Label full hours in the header and expose exact quarter-hour values on focus. An optional detail view may use fixed 40px slots and horizontal scrolling, but the presentation default is always the complete-day overview.

Each interactive segment is a real `<button>` with an accessible name containing crew, state, job, time range, exertion, and applicable rule IDs. Implement roving focus only if arrow-key navigation is completed and tested; otherwise preserve standard Tab order instead of publishing a partial ARIA grid.

### Visual semantics

- Activity state owns the segment fill.
- Heavy exertion adds a stripe or edge treatment.
- Crew identity uses the row label and a route stroke/marker.
- Selection uses a high-contrast outline.
- Diff meaning uses a text/icon badge in the detail area.

This prevents heat, crew, exertion, priority, status, and diff colors from competing on one block.

## 10. Schematic map implementation

The map is explicitly labeled **Schematic service map**. It displays the backend's schematic coordinates and route segments and makes no street-routing claim.

- Use one responsive SVG `viewBox`.
- Render depots as squares and jobs as circles.
- Use crew color for route strokes, not for every data meaning.
- Crossfade old and new routes; animated route drawing is optional polish.
- Synchronize pointer selection with the timeline and diff list.
- For keyboard access, use positioned HTML buttons over nodes or focusable SVG groups with Enter/Space handling. A bare SVG circle with `role="button"` is insufficient.

The timeline and diff list remain complete keyboard alternatives if map interaction is unavailable to a screen-reader user.

## 11. Shell, responsiveness, and motion

Use one top ChapterNav and one bottom TrustBar. The TrustBar contains the policy disclaimer on the left and solver evidence on the right. Both bars reserve layout space; neither may cover content.

| Viewport | Required behavior |
|---|---|
| `>= 1280px` | Two-column map/timeline composition; full-day timeline visible |
| `1024–1279px` | Map stacks above timeline; full-day timeline still visible |
| `768–1023px` | Reduced padding; metrics wrap; all interactions remain available |
| `< 768px` | In-flow “optimized for laptop” advisory; content remains usable and unblocked |

Motion uses `transform` and `opacity` only where practical. Respect `prefers-reduced-motion: reduce` with an immediate data swap and static diff markers. Provide a replay control for the presenter. Never use scroll hijacking.

## 12. Accessibility acceptance

- A skip link is the first focusable control.
- Chapter changes move focus to the new chapter heading.
- Every action is a native button with visible focus.
- Timeline facts are reachable by keyboard without depending on hover.
- Color is paired with status text, icon, label, or pattern.
- Solver completion and diagnosis updates use polite live regions.
- Errors use an assertive live region only when immediate attention is required.
- Minimum caption size is 12px; critical evidence should be 13px or larger.
- At 200% browser zoom, content reflows and no control is covered by the shell.
- Reduced-motion mode contains no required information only visible in animation.

## 13. Focused verification

Automate the smallest tests that protect the demo contract:

1. The saved fixture renders all three chapters and carries a visible saved-run disclosure.
2. Solver statuses produce the exact allowed claims; only `maximum_claim_allowed: true` permits “maximum.”
3. All 40 timeline slots and every returned segment render at the expected grid columns.
4. Selecting a changed job exposes the same job ID in timeline, map, and diff detail.
5. Diagnosis renders classification, proof status, retained commitments, and objective delta from the response.
6. A +2°C request sends the right input and displays the returned changed decision.
7. Network/server failure uses only a matching fallback entry; validation failure remains visible.

Then perform a manual pass at 1280×720 and 1440×900:

- complete the three-chapter keyboard journey;
- inspect focus, contrast, overflow, and the TrustBar;
- run with reduced motion;
- disconnect the API and complete the saved-results journey;
- record one uninterrupted 3–5 minute demo rehearsal.

## 15. Build and serving

Configure Vite to emit into `backend/heatshift/static/`. In development, proxy `/api` to FastAPI. In production, FastAPI serves both `/api/*` and the compiled single-page application from the same origin.

Environment switches:

| Variable | Default | Purpose |
|---|---|---|
| `VITE_API_BASE_URL` | empty | Same-origin API by default |
| `VITE_FALLBACK_MODE` | `false` | Explicitly force the saved-results rehearsal path |

Production verification:

```bash
cd frontend
npm ci
npm run test
npm run build
```

The release is not complete until a fresh backend start serves the compiled UI, `/api/*` still resolves correctly, direct loading of the app route works, and the fallback file is included in the build.
