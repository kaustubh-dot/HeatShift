# HeatShift Implementation Master Plan

## 1. Purpose

This document is the single execution index for HeatShift. It converts the locked product documents into small implementation packets that can be assigned one at a time to a coding model with limited context.

No implementation agent may redesign the product, change solver meaning, weaken a release gate, invent demo outputs, or begin a later phase early. If code reveals a genuine contradiction, stop, record it in `CHECKPOINT.md`, and correct the source contract before continuing.

## 2. Planning status

**Planning is frozen.** The only permitted documentation changes after this point are:

- implementation-driven corrections to an impossible or contradictory contract;
- exact dependency/version recording;
- checked task status and checkpoint evidence;
- deployment details discovered from the working build; and
- final measured metrics, screenshots, or limitations.

New features, personas, integrations, visual modes, optimization goals, and policy semantics are out of scope.

## 3. Source-of-truth order

When documents overlap, use this order:

4. [ARCHITECTURE.md](ARCHITECTURE.md) — component boundaries and ownership
5. [PRD.md](PRD.md) — product scope and user outcomes
6. [SAFETY_AND_LIMITATIONS.md](SAFETY_AND_LIMITATIONS.md) — permitted and prohibited claims
7. [DEMO_SCENARIO.md](DEMO_SCENARIO.md) — fixture narrative and tuning limits
8. [DESIGN.md](DESIGN.md) — visual and accessibility behavior
9. [FRONTEND_PLAN.md](FRONTEND_PLAN.md) — frontend execution details

Never silently choose between contradictory sources. Record the exact conflict and stop that task.

## 4. Frozen implementation decisions

- Python 3.12 for the backend.
- OR-Tools CP-SAT for optimization.
- Pydantic for request and fixture models.
- FastAPI for the HTTP boundary.
- Pytest for backend verification.
- React, TypeScript, and Vite for the frontend.
- React reducer/context for application state; no state library initially.
- Vanilla CSS; no CSS framework or runtime CSS-in-JS.
- Native `fetch`; no HTTP client library.
- One process boundary in production: FastAPI serves `/api/*` and compiled frontend assets.
- Bundled JSON inputs and genuine saved solver outputs; no database.
- One deterministic scenario, one declared tuning pass, and one perturbed regression scenario.
- No internet dependency in the core demo.

## 6. Agent execution protocol

Every implementation turn follows this exact sequence:

1. Read `CHECKPOINT.md`.
2. Read the task row in this document.
3. Read the complete task packet in the linked implementation plan.
4. Read every source-of-truth document named by that packet.
5. Inspect existing files and callers before editing.
6. Implement only the active task.
7. Run the narrow tests required by the packet.
8. Inspect the complete diff once.
9. Remove unused additions and unrelated edits.
10. Check the matching `TODO.md` item only after the acceptance condition passes.
11. Update `CHECKPOINT.md` with commands run, evidence, next task ID, and any limitations.
12. Stop. Do not begin the next packet in the same turn unless explicitly instructed.

An agent must not report completion based only on files existing. Completion requires the packet's named verification command and expected evidence.

## 8. Release gates

### Gate G1 — Inputs and patterns

Pass only when B00–B05 are complete and:

- all fixtures validate;
- every mandatory/locked job has an eligible crew;
- the six job-local pattern cases plus generator determinism pass; the consecutive-job global case is reserved for B06;
- recovery and stop-work behavior come from the submitted policy; and
- no generated output metric is hardcoded.

### Gate G2 — Solver evidence

Pass only when B06–B15 are complete and:

- the recommended plan has zero mandatory conflicts;
- the service-first plan has at least one visible policy conflict;
- critical service is preserved where genuinely feasible;
- at least two meaningful schedule changes occur;
- at least one planned job is deferred or substituted;
- one forced-inclusion diagnosis is nontrivial;
- +2°C changes at least one meaningful decision;
- route and metric reconciliation are exact;
- statuses and bounds support every optimization claim; and
- saved output is reproducible.

If this gate fails, use the single permitted fixture-tuning pass in B14. Do not weaken policy rules or objective ordering.

### Gate G3 — API

Pass only when B16–B17 are complete and:

- all three endpoints match the canonical schema;
- invalid input never reaches the solver;
- feasible incumbents return HTTP 200 with honest proof state;
- no-result timeouts and model errors use the common error envelope; and
- the bundled solve meets the measured demo runtime target.

### Gate G4 — Frontend

Pass only when F00–F12 are complete and:

- all displayed facts come from API/fallback fields;
- the full timeline fits 1280×720 in overview mode;
- a judge can understand the before/after result in 30 seconds;
- keyboard and reduced-motion journeys complete;
- saved-result mode is visibly disclosed; and
- the production UI is served by FastAPI without runtime CDN access.

### Gate G5 — Submission

Pass only when R00–R04 are complete and the submitted repository, video, presentation, installation instructions, licenses, and live/demo link all refer to the same release build.

## 9. Checkpoint format

After every task, replace the mutable section of `CHECKPOINT.md` with:

```markdown
## Active implementation checkpoint

- Last completed task: B00
- Verification command: `exact command`
- Result: `exact pass count or generated artifact`
- Files created/changed: `short list`
- Known limitation: `none` or one precise fact
- Next task: B01 — Canonical Pydantic models
```

Do not write “tests pass” without the command and count. Do not mark a gate passed without listing its evidence.

## 10. Handoff format for implementation agents

Every coding agent ends with exactly these five items:

1. **Outcome:** one sentence describing what now works.
2. **Files:** exact files created or changed.
3. **Verification:** commands and pass/fail counts.
4. **Contract notes:** assumptions, proof limitations, or `None`.
5. **Next task:** the next task ID only; do not start it.

## 11. Stop conditions

Stop the active task and request a planning correction when any of these occurs:

- a required field or status has no canonical definition;
- a test would require inventing policy meaning;
- a proposed shortcut changes an observable solver claim;
- a genuine output cannot satisfy a scenario gate without modifying policy or objectives;
- two source-of-truth documents conflict;
- the requested dependency does not support Python 3.12;
- implementation would require personal, medical, live GPS, or external municipal data; or
- a later phase is requested before its release gate passes.

Do not stop merely because a test is difficult. Diagnose the smallest failing invariant and report the evidence.
